## Bugs the tests caught (and fixed)

1. **mmCIF chain grouping by `auth_asym_id` merged distinct polymers** — 6X18 reuses author chain
   IDs across entities. Now grouped on `label_asym_id`. This would have silently fused the target
   with an unrelated chain and corrupted both sequence and coverage.
2. **`build_manifest` collected errors instead of failing closed**, so a predicted model could have
   entered a manifest as a `rejected` note while other rows looked valid. Now raises on the first
   bad input; `fail_closed=False` is opt-in for inventory-only runs.
3. **Non-polymer records (waters/ions/ligands) were being folded into chain sequences** and could
   appear as `X`. Now excluded from polymer chains and counted separately (`hetero_records`).

## Fixed a real defect in the existing validator
`scripts/c5_validate_submission.py` shipped with defaults that **contradicted the official
competition schema** recorded in `results/c5_constraints_review.md`:

| item | was | now (official) |
|---|---|---|
| allowed `molecule_class` | `single_chain` (a C3/C4-only value) | `single_chain,nanobody,scfv,fab_kappa,fab_lambda` (corrected 2026-10-25; the official form/template use `single_chain`, not the FAQ's `protein`) |
| length window | 40–200 aa | **10–250 aa** |

Left as-is, a valid C5 file would have failed and an invalid one could have passed. Also added:
- fab entries are now split on `:`/`|` **even without** `--vh-vl` (the class implies two chains),
  and VH/VL lengths are checked for fab classes too;
- a fab with no separator gets **one** clear error ("requires VH:VL in one field") instead of
  cascading "length 0" errors;
- a missing `molecule_class` column produces **one** error, not one per row;
- `--classes ""` now disables the class filter instead of raising.
Every limit remains overridable — the track is still unpublished, so nothing is hard-coded.

# C5 prep, part 3 — 2026-10-25 07:05 ET (CPU only, $0 GPU, no network)

## Closed the last missing Kimi §3 deliverable: a resumable, budget-stopped runner
Kimi's §3 asked for "resumable runner with artifact retrieval, provenance and budget stops".
Parts 1–2 delivered the validator, templates, target-input validator and template tooling; the
runner did not exist. It does now.

| file | sha256 | tests |
|---|---|---|
| `c5_prep/resumable_runner.py` | `ddf4d0da8297…` | — |
| `tests/c5/test_c5_resumable_runner.py` | `39a0d84ade98…` | **32/32 pass** |

**Target-independent by construction.** It knows nothing about the C5 target, assay or track. It
runs a caller-supplied command per row of a caller-supplied CSV, so it is pure infrastructure.

### Guarantees (each enforced in code, each covered by a test)
1. **Resumable** — JSON state keyed by job id and input-row sha256. Completed jobs skip. An
   artifact whose sha256 no longer matches its record is *not* treated as done; it re-runs.
   Atomic state writes, so a crash mid-save cannot corrupt resumability.
2. **Budget stop** — wall-clock and dollar ceilings checked **before each launch**; a run that
   cannot afford the next job stops cleanly with exit **2**. `--max-usd` is **required** — no run
   can start without an explicit budget. (My first draft defaulted it to 0.0 and silently blocked
   every launch; the test suite caught it before this was written up.)
3. **Fail closed** — nonzero worker exit, missing artifact, or empty artifact is recorded `failed`
   and never counted `done`; final exit **3**. Malformed state or a missing id column exits **4**.
4. **Provenance** — per job: command argv, start/end timestamps, duration, exit code, artifact path
   and sha256, input-row sha256. Per run: version, limits, elapsed, spend estimate, state-file hash.

### Validated on a real fixture, not just synthetic tests
Ran all **182** rows of `results/c3_r3_20261025/screen_input_20261025.csv` through a fake worker:
**182/182 done in 4.9 s**, then a resume launched **0** jobs. A bad id column exited **4**; a worker
producing no artifact exited **3**; shell metacharacters in a command were not evaluated.

One portability defect found and fixed during that run: the ID column is now configurable
(`--id-col`), because the real C3 fixture names its key `name`, not `id`.

### What this does NOT do
No target, epitope, scaffold, sequence, threshold or GPU allocation is pre-committed. No GPU, no
network, no spend. It does not by itself make C5 ready; it removes one concrete blocker from the
Monday path.
